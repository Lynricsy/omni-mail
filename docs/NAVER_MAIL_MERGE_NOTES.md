# NAVER Mail 主线合入与 D1 迁移注意事项

本文记录 NAVER Mail 合入主分支时的数据库迁移约束。后续维护者在新增邮箱适配或修改
Cloudflare D1 schema 前必须先阅读本文件。

## 迁移编号决定

- `main` 的最后一个既有正式迁移是 `0031_qq_mail_identities.sql`。
- `0032_netease_mail.sql` 只在未合入主线的网易邮箱测试分支和少量测试数据库中使用。
- 网易邮箱因 Cloudflare Worker 无法稳定连接上游服务，不合入主分支。
- NAVER Mail 保留已经验证和部署过的 `0033_naver_mail_imap.sql`，不改名、不降号。
- `0032` 视为永久保留/废弃编号；主分支不得新增任何 `0032_*.sql` 文件。
- NAVER 合入后的下一个正式迁移必须从 `0034` 开始。

不要为了让编号连续而增加空的 `0032` 迁移。迁移文件名是 D1 已应用记录的一部分；同一个
迁移身份在不同安装中不能代表不同 SQL。Cloudflare D1 会把迁移名称记录在
`d1_migrations` 表中，并应用尚未记录的迁移文件：

<https://developers.cloudflare.com/d1/reference/migrations/>

## 兼容场景

| 数据库状态 | 合入 NAVER 后的行为 |
| --- | --- |
| 全新安装 | 按顺序应用 `0001`–`0031`，跳过保留编号，再应用 `0033` |
| 已安装 OmniMail `0.7.2` | 只应用 `0033_naver_mail_imap.sql` |
| 曾部署网易测试分支 | 保留已记录的 `0032_netease_mail.sql`，再独立应用 `0033` |
| 已部署过 NAVER 测试版本 | 识别完整文件名已经应用，不重复执行 `0033` |

测试期遗留的网易表和迁移记录不由 NAVER 发布删除。删除遗留 schema 属于独立的破坏性清理，
不得混入功能合并或普通部署。

## 实现约束

1. 远程部署继续按 `d1_migrations.name` 的完整文件名集合计算待执行迁移，不得改为只比较最大
   数字版本。
2. `WRANGLER_MIGRATION_NAMES` 可以从 `0031` 直接列到 `0033`，不需要伪造 `0032`。
3. 运行时 `REQUIRED_MIGRATION` 使用 `0033_naver_mail_imap.sql`，并保留 NAVER 的可恢复建表语句。
4. 已经发布或部署过的迁移文件不得重命名、改号或替换成不同 SQL。
5. 如果以后重新评估网易邮箱，必须基于当时主线创建新的最新编号迁移（至少 `0034`），同时把
   运行时快速检查更新到该最新迁移；不得重新使用旧的 `0032` 文件。

## 合入前验证

- 从当前 `main` 创建 NAVER 合入分支，不直接合并旧功能分支覆盖后续修复。
- 覆盖以下迁移测试：
  - `0031 → 0033`；
  - 已有 `0032_netease_mail.sql → 0033`；
  - 已有 `0033` 时重复部署保持幂等。
- 验证 NAVER 同步单轮边界和过期租约恢复，避免重复引入 QQ/Gmail 已修复的大邮箱同步问题。
- 运行 Web/Node 全量测试、Worker 测试、TypeScript/Oxlint 和生产构建。
- 检查主线差异不包含网易邮箱路由、前端入口、Worker 调度或 `0032_netease_mail.sql`。
- 部署前确认 `NAVER_MAIL_CREDENTIALS_KEY`、环境开关和管理员入口开关符合发布策略。

## 回滚边界

回滚 Worker 代码时不回滚或删除 `0033` 表。关闭 NAVER 环境开关和管理员入口即可停止新连接、
同步、正文读取和后台任务；保留 D1 数据可避免回滚过程中破坏用户账号和密文。
